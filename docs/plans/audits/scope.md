# AbletonLiveMCP v1 scope audit

Status: Draft recommendation; research only. Reviewed 2026-11-10.

**Recommendation:** ship a dependable, stock-first chain and Session View assistant. Its differentiator should be translating a small set of musical roles and physical settings into devices the user can actually control, with an inspectable plan and honest readback. Preserve rack/macros, usage-derived drum racks, and browser organization as explicit roadmap commitments, with feasibility gates. They are not sufficiently implemented or verified to be v1 promises.

The supported baseline remains **Live 12.2+ with capabilities checked individually**, following the corrected decision in `docs/vision.md`. The owner's recorded runtime is 12.2.0, not 12.4. Do not raise the baseline merely to acquire 12.3 APIs: those APIs still do not establish macro mapping or browser tagging.

Read: README, vision, original prompt, stale handoff, lessons, every file under `src/abletonlivemcp/`, all scripts, Remote Script handlers/core/entry point, packaging, contributor instructions, selected tests, and the knowledge index. Existing unrelated changes in `knowledge/`, `research/`, and `tasks/` were left alone. No Live connection, port 9877 access, script execution against Live, implementation, commit, or publication occurred. This report is the only file written.

**Status definitions:** DONE means the narrow behavior exists in code, not that this audit ran it in Live. PARTIAL means some necessary steps exist. MISSING means no implementation of the promised outcome was found. Historical Live observations are attributed to the handoff or stored probe data; none are new verification. Tests were inspected, not executed: this is a documentation-only audit and its instructions prohibit Live access.

The knowledge base is a **development resource, excluded from distribution**. Its breadth does not expand the runtime's four supported roles or constitute a shipped musical reasoning engine. The external MCP client supplies language understanding and musical judgment; the server supplies bounded operations and curated mappings.

## 2. Tool-surface review

### Current surface and naming changes

There are **38 decorated functions: 35 always registered and three conditional knowledge tools**. Normal installs should omit the three knowledge tools. Neither the handoff's 27 nor “38 shipping tools” is an accurate stable product description.

Adopt `live_<verb>_<object>` consistently, with `get` for one object and `list` for collections. Use `launch` consistently for clips/scenes. Keep offline/library utilities under a separate prefix. Make one deliberate pre-v1 rename, update examples, and avoid permanently advertising both old and new aliases to the LLM.

| Current tool(s), covering every declaration | Concrete recommendation | Reason / priority |
|---|---|---|
| `live_hello` | Rename `live_get_status`; include versions, connection status and meaningful capability states. | Handshake is useful, but “hello” is opaque. MUST. |
| `live_session_info`, `live_tracks` | Rename `live_get_session`, `live_list_tracks`; add focused `live_get_track`. | Current session has counts only; track enumeration omits returns/master, mixer and clip slots. Avoid fetching every device to answer a simple track question. MUST. |
| `live_browser_roots`, `live_browser_list`, `live_browser_search` | Rename `live_list_browser_roots`, `live_list_browser_items`, `live_search_browser`; retain all three operations. | Roots, browsing and search have distinct purposes. Add real pagination/continuation and complete/truncated/unknown semantics. MUST. |

### Contract problems that matter more than adding tools

1. **Plan completeness:** `_map_intent()` drops unknown/untranslatable intentions into notes. `build.ok` can still be true after those intentions vanished. Return explicit `applied`, `substituted`, `unmapped`, `uncalibrated` and `failed` fields; success must describe the whole requested intent. Permit partial execution only when its exact omissions are explicit in the submitted plan.
2. **Target identity and placement:** loading selects a track but not a defined insertion target. Checking `devices_after == devices_before + 1` does not prove the new device is last; the builder then writes to `devices_after - 1`. Validate the actual added object/position and protect against user edits between calls. For v1, support append onto empty tracks first; expand to occupied chains only after passing that scenario in Live.
3. **Execution outcomes:** name validation happens before loading, but parameter validation happens after loading and chain execution is not transactional. A later exception loses the structured record of earlier changes. Return completed stages and exact failure location, stop at that point, and never retry a possibly completed write automatically. Do not promise rollback until proven. A small plan fingerprint plus fresh preconditions is enough; a durable transaction engine is unnecessary.
4. **Physical meaning:** numeric display matching is valuable. Raw targets are currently marked `exact=True` without checking the returned raw value; that does not validate their physical meaning. VintageVerb decay values are explicitly uncalibrated guesses and predelay is unmapped. Disable guessed physical conversions in default v1 execution; show omissions or choose stock instead. Distinguish solver tolerance from exact equality.
5. **Static plugin access:** Pro-Q 3 and Pro-R being “opaque” is a result for the probed instances, not a permanent property of those products. Required controls can change after Configure or loading a prepared preset. Conversely, “full” does not mean the adapter maps every relevant parameter. Validate the requested controls, enabled state, mode dependencies and automation state on the actual instance.
6. **Bounds and discovery:** browser limits are checked only around the outer traversal loop, so one large child list can exceed the node/result budget. Lists truncate at 200 without continuation; plugin resolution ignores `budget_exhausted`, making “not installed” too strong. Use `not found in searched portion` until traversal is complete. Bound planning to the same 12-stage maximum as execution.
7. **Schemas and errors:** nested `list[dict]`/`dict` parameters underdescribe stages, notes and preferences to an LLM. Add typed nested models/enums and one units convention. `_tool` exposes ValueError/BridgeError cleanly, but offline `AlsError`, filesystem errors and `JudgeError` can still become opaque errors. Normalize expected failures with actionable details. Add MCP read-only/destructive/idempotency annotations supported by the installed SDK.
8. **Readback timing:** 0.3-second sleeps are a measured workaround, not proof a quantized launch has completed. Report pending/triggered versus playing, and allow a later bounded read. Scene launch currently returns immediately, unlike clip launch. Do not label every mutation as verified just because a call returned.

### Upstream parity: explicit scope change required

Inspected upstream at commit [`9dddc7bd5b95412510fdeb745949e3bf23f3fd8a`](https://github.com/ahujasid/ableton-mcp/commit/9dddc7bd5b95412510fdeb745949e3bf23f3fd8a), specifically [MCP_Server/server.py](https://github.com/ahujasid/ableton-mcp/blob/9dddc7bd5b95412510fdeb745949e3bf23f3fd8a/MCP_Server/server.py) and its Remote Script. This establishes a comparison baseline, not proof all upstream tools work.

- **Covered or close:** session information, handshake, audio/MIDI track creation, track naming, MIDI clip creation/add/read notes, device parameter reads/writes, tempo, browser discovery/loading, clip launch/stop and transport.
- **Partial:** focused track information, richer session snapshots and browser identity/loading. `load_drum_kit` is at most a generic-loader candidate here; it was not tested.
- **Missing production workflows:** `create_audio_clip`, `clear_notes_from_clip`, `set_clip_name`, `delete_clip`, `set_arrangement_clip_name`, `get_arrangement_clips`, `duplicate_to_arrangement`, `switch_to_arrangement_view`, `set_arrangement_time`, `create_locator`, and a session snapshot with returns/master/racks.
- **Deliberately exclude:** dataset consent, intent/rating/preference/rejection/audition collection and trajectory recording infrastructure. These do not belong in this no-telemetry project.

Recommendation: replace the release claim “everything upstream can do” with a published workflow checklist and a frozen baseline. This is a proposed change from the founding parity promise, not an accomplished decision. Keep practical audio/clip editing in SHOULD; schedule Arrangement parity later. Do not chase upstream growth or copy its data collection to satisfy an unbounded tool-count promise.

## 3. Live API feasibility and evidence

A documented operation still needs a Python runtime check on the supported version. Current LOM pages are moving references; an absent “since” marker does not prove availability on 12.2. Negative findings below mean “no supported method found,” not mathematical impossibility.

## 4. Recommended v1

### MUST: the release contract

1. **One supported installation path that works outside a checkout.** Ship both MCP and Remote Script assets, document enabling the control surface and stdio client setup, report bridge/server/Live versions, and give clear disconnected/version-mismatch errors. `pyproject.toml` currently includes only `src/abletonlivemcp` in the wheel, while `install.source_dir()` expects a sibling repo-level `remote_script` directory: normal-wheel installation is a concrete packaging gap. Packaging compatibility with the declared Python/MCP versions must also be checked in a clean environment.
2. **Stock-first inspection and Session workflows.** List tracks/scenes/clip slots, inspect devices/parameters, create/name/color tracks and MIDI clips, add/read notes, launch/stop and set tempo. Include existing returns/master in applicable inspection/device/mixer addressing. Publish a specific workflow checklist instead of universal near-native parity.
3. **Minimum mixing controls.** Read/set gain, pan, mute/solo and existing sends, with physical-unit readback and explicit targets. This supports daily use of chains. Do not grow this into a complete mixing console.
4. **One chain planning/execution path.** Support the existing four roles and exact-device stages; preferences; deterministic stock fallback; both existing vocal starting presets; plan report; explicit intent omissions; actual inserted-device identity; bounded execution; full success/partial/failure accounting. Do not silently rebuild a changed plan or convert “unknown inventory” into “not installed.”
5. **Tested plugin support, not universal plugin claims.** Validate Pro-C 2's currently mapped controls as the first optional third-party adapter. Generic loading and parameter inspection remain available for other installed plugins. Treat VintageVerb physical decay as unsupported until calibrated; retain honest stock substitution. Report capabilities per requested intent and current configured instance.
6. **Sensible starting points with limits.** Label preset numbers as starting conventions, not artist settings, measured loudness or guaranteed gain reduction. Explain inline versus return intent. Do not choose uncalibrated values silently or infer what sounds right without audio evidence.
7. **Reliable client contracts.** Typed stage/note/preference models; consistent names/units; bounded pagination; actionable errors; no blind mutation retries; honest pending-launch state; no hidden paid network dependency. The normal install has no knowledge tools, no telemetry, and local-only default classification behavior if that extension is enabled.
8. **Lean release proof in real Live.** Pass the acceptance stories below in disposable Basic using stock devices first. Run existing offline checks once at the implementation release gate, fixing actionable failures without expanding fake-Live tests. Record exact versions and observed results. This audit does not satisfy that gate.

### SHOULD: useful if they fit after MUST is solid

- Add/create a return track and set a validated output route; demonstrate a wet stock reverb return and dry-vocal send.
- Add stock delay and Utility role support with one measured adapter each; these are more useful than a large untested plugin catalog. De-essing needs its own intentional mapped recipe, not a gear-description string.
- Add audio import, bounded note edit/delete and clip duplication/deletion as practical workflow parity beyond the MUST clip naming/color controls, without expanding into Arrangement editing.
- Read nested rack devices/macros, rename devices, and load existing user-made `.adg`/`.adv` presets via the browser after verification. Reading an existing rack does not imply creating or editing its macro mappings.
- Harden and expose the optional offline Set/usage profile: structured samples/provenance, correct trigger evidence, explicit selected roots, accurate Set-file counts, bounded scans, and clear missing/corrupt-file reporting.
- A short adapter authoring guide with required controls, units, plugin format/version, capability probe and a real-Live acceptance example. Existing `scripts/live_*.py` are a starting point; make acceptance failures return nonzero rather than relying on printed `FAIL`/`OFF` text.

### WON'T-YET: deliberate cuts

| Cut from v1 | Why; condition for reconsideration |
|---|---|
| Group an arbitrary existing chain and automatically name/map macros | Core founding goal, but missing implementation plus unverified mapping/name/range route. Preserve it as the first bounded feasibility milestone; stock FX require no audio/sample provisioning. |
| Generate/export arbitrary `.adg` / `.adv` files or round-trip VST state | Reverse-engineered formats and identity/state preservation need a proven template route. Separate generating a new rack from capturing an existing live chain. |
| Build a Drum Rack from recent projects | Too many unfinished layers: recent/genre selection, sample evidence, classification, layout, pad loading, sample paths and preset acceptance. First ship a defensible read-only usage report, then explicit-sample rack construction. |
| Automatic browser Collections/color/tag/database edits | No verified supported writer or safe reload contract. Category/frequency recommendations may be useful, but must not be advertised as applied browser organization. |
| Any installed plugin; automatic Configure; arbitrary vendor preset/state support | Parameter exposure and conversion are instance/product/version dependent. A small adapter contract scales better than guesses from names. |
| Artist article ingestion and exact emulation matching | Needs sourced structured gear relationships and settings provenance; external LLM interpretation plus an explicit user-approved role plan covers the narrower v1 case. |
| Arrangement automation, MIDI expression, recording/export, freeze/flatten, track grouping | Adds breadth outside the chain/Session outcome; some API routes need independent validation. Continue reporting gaps rather than adding unsupported tools. |
| Embedded producer agent, automatic audition/judging, paid classification backend in core | The user directs. Remote classification adds cost/privacy/configuration surface without completing current Live workflows. No need for an in-server model to implement adapters. |
| Shipping `knowledge/` or expanding it as a release deliverable | It is explicitly a development resource. Ship only deliberately curated original adapter/preset data needed by the small supported feature set. |

Future bundled templates/data must have compatible provenance; no commercial plugin state, audio, or unlicensed preset assets should be included by default.
